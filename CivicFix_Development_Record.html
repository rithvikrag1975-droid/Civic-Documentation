August 17, 2026
Time worked · 1.5h

Project start: Good Neighbor agent concept

Established the original hackathon direction and the first technical environment.

The project began under the AWS Agents for Humans hackathon as a “Good Neighbor” concept centered on local library work. The early idea was to reduce repetitive administrative workload around programs, registrations, resource promotion, and routine resident questions.

  • Defined the first end-to-end workflow for a community-service agent.
  • Set up Python 3.12 as the project runtime.
  • Installed the Strands Agents SDK and began learning how agents and tools would fit together.
  • Started thinking in terms of a real task workflow instead of a chatbot-only experience.

Result

A working development environment and a first community-service problem space.
Next step

Finish AWS access and decide whether the library concept is strong enough for the project.

Time worked · 1.25h

AWS access, authentication, and project comparison

Prepared the cloud environment and compared stronger community-agent directions.

Work focused on the practical AWS setup needed for Strands and Amazon Bedrock. AWS CLI access, IAM credentials, and authentication were configured and verified so local Python code could call AWS services.

  • Installed/configured AWS CLI and verified the account identity.
  • Worked through IAM access required for Bedrock model invocation.
  • Received hackathon credits and confirmed that cloud development could continue.
  • Compared multiple “Good Neighbor” ideas and questioned whether the library workflow was distinctive enough.

Result

AWS infrastructure became usable and the project was ready for a stronger concept.
Next step

Select a more technically differentiated community problem.

August 19, 2026
Time worked · 2.0h

Pivot to CivicFix

Reframed the project around civic infrastructure reporting and government routing.

The project pivoted away from the library concept and became CivicFix: an assistant for residents reporting non-emergency civic problems. Mercer County was selected as the initial geographic scope so the prototype could be narrow enough to finish while still dealing with real jurisdiction complexity.

  • Defined CivicFix’s purpose: identify problems, determine the responsible government level, prepare reports, and eventually support submission/tracking.
  • Outlined separate intake, jurisdiction, routing, action, and tracking responsibilities.
  • Planned for a future mobile client while keeping the backend reusable.
  • Completed the Bedrock/Anthropic access process needed for the AI-agent portion.

Result

CivicFix became the primary project with Mercer County as the MVP scope.
Next step

Turn the concept into a concrete end-to-end workflow and begin the jurisdiction core.

August 21, 2026
Time worked · 0.75h

Human-approved workflow refinement

Clarified how CivicFix should do real work without blindly acting on a resident’s behalf.

The project flow was refined around a human-in-the-loop design. CivicFix should prepare the correct action and only move forward when the resident has enough information to review what will happen.

  • Separated issue understanding from jurisdiction determination.
  • Clarified that deterministic government data should be preferred over AI guesses.
  • Kept government submission connectors as a later integration rather than pretending every agency exposes an API.

Result

A more defensible architecture: AI interprets; authoritative systems decide factual routing where possible.
Next step

Build the actual agent/tool pieces and prove jurisdiction routing with code.

Intake Agent, Jurisdiction Agent, and first tool

Built the first functioning multi-part CivicFix reasoning workflow.

CivicFix gained working agent components. The Intake Agent classified reported non-emergency problems, while a separate Jurisdiction Agent was given a Strands tool for road-maintenance lookup. The first lookup used a small hard-coded dictionary as a teaching and integration scaffold.

  • Created the Intake Agent with structured JSON-style issue output.
  • Created jurisdiction_agent.py.
  • Created road_tools.py with @tool and lookup_road().
  • Tested Route 33 successfully as state-maintained.
  • Used Route 54 to expose the limitation of hard-coded road data.

Result

The agent could call a Python tool, but the road data needed to become real and scalable.
Next step

September 6, 2026
Time worked · 2.25h

Real NJ ArcGIS road data integration

Moved from fake road ownership data to real GIS-backed jurisdiction lookup.

The largest technical step so far was integrating New Jersey’s ArcGIS transportation road data through Python’s requests package. The API response structure was explored and parsed so CivicFix could translate government road-jurisdiction codes into readable jurisdiction values.

  • Queried the NJ transportation ArcGIS service.
  • Identified PRIMENAME as the road name field and JURISDICTN as the jurisdiction field.
  • Learned and implemented JSON traversal through features → [0] → attributes → JURISDICTN.
  • Mapped S → state, C → county, and M → municipal.
  • Tested state, county, and municipal road examples.
  • Compared exact searches with broader LIKE searches and saw why loose road-name matching can be risky.

Result

CivicFix could retrieve real road-jurisdiction information from NJ GIS instead of asking the AI to guess.
Next step

Move the proven API logic into the real Strands tool and handle ambiguous matches more safely.

September 21, 2026
Time worked · 1.75h

Real tool integration + mobile/location redesign

Connected the live GIS lookup to the agent, found the road-name ambiguity problem, and redesigned the MVP around map coordinates and evidence.

The working API request was moved into road_tools.py. A dynamic f-string bug was diagnosed and fixed, after which the tool correctly returned state, county, and municipal results. The Jurisdiction Agent was reconnected to the real tool. Testing then revealed a more fundamental design issue: a road-name search can return multiple matching segments and blindly selecting the first match is not reliable enough.

  • Replaced the practice road dictionary with the real NJ GIS API call.
  • Added safe handling for empty features results and an unknown fallback.
  • Fixed (road_name) to {road_name} inside the f-string query.
  • Verified State Highway 33 → state, English Creek Road → county, and Hunter Avenue → municipal.
  • Reconnected the Jurisdiction Agent to the real lookup tool.
  • Identified that coordinate-based lookup is safer than first-match road-name lookup.
  • Redesigned the planned app around an interactive map, current-location button, and manual pin placement.
  • Defined evidence capture: close-up photo, surrounding/context photo, and optional video.
  • Set the one-month goal as a working Mercer County prototype.

Result

The project moved from a road-name demo to a clearer mobile MVP: location + evidence + AI + GIS + structured report.
Next step

Build latitude/longitude → exact road segment → jurisdiction, then connect that to the mobile map UI.

Prototype architecture

The intended end-to-end flow for the Mercer County version of CivicFix.

01 · Locate
Map + GPS

Use current location or manually place a pin if the user already left the area.

02 · Document
Text + evidence

Description, close-up photo, surrounding photo, and optional video.

03 · Understand
AI analysis

Classify the civic issue and check whether the evidence provides useful context.

04 · Route
NJ GIS

Use coordinates to identify the actual road segment and responsible jurisdiction.

05 · Prepare
Structured report

Present the resident with a clear reviewable report and appropriate routing destination.

Prototype boundary: Mercer County. Government submission and tracking are later integrations; the current project does not assume that every agency exposes a usable API.
